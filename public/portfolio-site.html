About

About Emily.

Emily is a product designer working on agentic UX: the layer of a product that decides how an AI plans, acts, recovers, and explains itself. Currently at Roblox, designing the Studio Assistant experience used by millions of creators.

The work spans the full range of the discipline. North star vision documents that set direction for multi-year roadmaps. Systems design for features like planning, skills, and checkpoints. And working prototypes in React and Three.js, because some questions only answer themselves at fidelity.

The through line: interfaces for AI should be legible, reversible, and consistent. People deserve to understand what a product is about to do, and to change their mind after it does it.

Based in San Francisco. Off hours: knitting, baking, and a very good dog named Goose.

Planning Mode

Giving Roblox's AI Assistant a place to collaborate with the creator before it acts. Creators can review and direct intent before creation begins.

Role
Designer
Product
Roblox Studio Assistant
Year
2026

The problem

Agentic assistants act fast, and speed without visibility erodes trust. Creators watched the assistant edit scripts and scenes with no window into intent. When results missed, the only recourse was undo and retry, an expensive loop for complex builds.

The core question: how does an assistant show its thinking in a way that invites steering, without slowing down people who already trust it?

Principles

Three principles from the assistant north star anchored every decision in this work.

Legibility

Every action can be read and understood before it happens. Plans use plain language, never tool syntax.

Reversibility

Every action can be walked back after it happens. Plans pair with checkpoints so trying is cheap.

Consistency

The plan structure carries through review, execution, and history. One mental model, three moments.

The flow

Planning became a distinct, reviewable state between intent and execution. The same structure persists across the whole turn, so the model built during review carries through to completion.

Plan · 4 stepsEditable
Create GuardTower model in WorkspaceDone
Write patrol script for the tower NPCIn progress
Wire waypoints to existing terrain nodesRevise
Playtest and summarize resultsRevise
The plan card mid-execution: completed, active, and pending steps share one structure. Replace with a product screenshot.
Plans are made to be edited, not just read.

Key decisions

Interrupt only at high stakes

Small, reversible edits execute directly. Multi-file or destructive changes surface a plan first. The threshold is a design decision, not a technical one.

Over: planning every turn, which taxes people who already trust the assistant.
Steps are conversational objects

Replying to a step revises just that step. Course correction costs one message instead of a restart.

Over: plan-level regeneration, which throws away everything that was already right.
Progress mirrors the plan

During execution the same structure becomes a live progress view. Nothing new to learn between approving and watching.

Over: a separate progress UI, which breaks the mental model at the exact moment trust matters most.

Outcome

Planning Mode shipped as a pillar of the assistant experience and set the pattern for how the product signals in-progress work.

Skills

A system for teaching an assistant new abilities.

Role
Designer
Product
Roblox Studio Assistant
Scope
Architecture to UI
Year
2025–26

The problem

Every creator wants the assistant to work their way: house conventions, preferred patterns, project-specific context. Custom instructions in a settings field don't scale past a paragraph, and prompt engineering shouldn't be a prerequisite for a personalized tool.

The core question: what is the unit of customization, and how does someone understand what the assistant has learned?

The architecture

The answer was a two-tier model. Skills are the container: a named capability with a master on/off switch. Commands live inside skills, each with its own activation mode. One switch controls the whole capability; fine-grained behavior lives one level down.

House Style
naming-conventionsAlways on
/review-scriptManual
lighting-presetsOn mention
The two tiers as they appear in settings: a skill with its master switch, commands with individual activation modes.
ModeWhen it runsDesigned for
Always onLoaded as context in every conversation.Conventions the assistant should never forget.
On mentionActivates when the topic comes up naturally.Domain knowledge that is only sometimes relevant.
ManualRuns only when invoked by name.Heavyweight workflows with side effects.

Inspectable by design

On disk, a skill is a folder: a manifest describing what it does, plus subfolders for commands and reference material. The file convention doubles as documentation, so a skill is inspectable by the person who installs it, not just the assistant that reads it.

house-style/ ├── SKILL.md what this skill does, and when ├── commands/ │ ├── review-script.md │ └── naming-conventions.md └── references/ └── style-guide.md
People trust customization they can inspect.

Key decisions

Scope started narrow

The MVP kept skills user-global and local, deferring sharing and sync. The mental model mattered more than the distribution story.

Over: launching a marketplace before the unit of customization was proven.
Edge cases were designed

Duplication renames predictably. Name collisions resolve with clear rules. The boring paths got the same attention as the demo path.

Over: patching behavior later, when conventions have already calcified.
The design system stayed in the loop

Settings UI shipped through a collaboration pass with the design systems team, so a new surface didn't mean new components.

Over: bespoke UI that would fragment the settings experience.

Skills established the customization model for the assistant and a settings pattern the rest of the product now builds on.

AI-Native Studio

The premise

Most AI features are bolted onto tools designed for direct manipulation: a chat panel docked beside a canvas built for a different era. This prototype flips the hierarchy. Conversation, canvas, and 3D workspace are peers, and windows exist to serve whichever mode of work is active.

The workspace concept: chat, viewport, and inspector as peer windows. Replace with prototype footage.

Built, not mocked

The prototype runs as a real application: a windowing system with a canvas-based genie effect (a 32×32 mesh deformation on minimize), multiple concurrent chats, and a 3D workspace rendered in Three.js. Building it for real surfaced problems a Figma flow never would: window focus and dragging conflicts, chat state across surfaces, rendering edge cases.

Building the real thing surfaced problems mockups never would.

Findings

Finding 01

Entry points matter more than the chat

The valuable moments happened when work started from the viewport or an asset, not from a text box. That finding fed directly into production roadmap thinking about invocation surfaces.

Finding 02

Agents need spatial affordances

When an agent works across windows, people need to see where attention is. The prototype tested focus indicators that later informed in-progress turn messaging.

Finding 03

Concurrency is a design problem

Multiple chats operating on one scene raised questions no single-thread flow ever forces: who owns the selection, and whose change wins.

Finding 04

Fidelity finds the real bugs

Window dragging conflicts, broken chat state, and rendering edge cases only appeared because the prototype was real. Each one became a design requirement.
